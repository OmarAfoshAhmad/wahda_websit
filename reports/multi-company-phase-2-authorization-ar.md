# تقرير المرحلة الثانية: التفويض المركزي

تاريخ التنفيذ: 2026-07-16.

## ما نُفذ

- أضيفت `src/lib/company-scope.ts` كطبقة خادم مركزية تشمل:
  - `requireSession()`
  - `requirePermission()`
  - `getAllowedCompanyIds()`
  - `requireCompanyAccess()`
  - `buildCompanyScope()`
  - `getAllowedServiceTypeIds()`
  - `requireServiceAccess()`
  - `buildFacilityVisibilityWhere()`
- لا تُقبل شركة أو خدمة من المتصفح إلا بعد تقاطعها مع العلاقات المستخرجة من قاعدة البيانات.
- `SUPER_ADMIN` يرى الشركات والخدمات غير المحذوفة/الفعالة كلها.
- بقية الحسابات تعتمد على `AccountCompanyAccess` و`AccountServiceAccess`.
- رؤية المرافق تعتمد على تقاطع الشركات مع `FacilityServiceCapability`، وليس `facility_type` وحده.

## إصلاح أمني في الأدوار

- أصبح `role_v2` أعلى أولوية من `is_admin` والأدوار النصية القديمة.
- `admin_benghazi` و`admin_tripol` لا يحتفظان بتجاوز المبرمج بعد تحويلهما إلى `MANAGER`.
- fallback إلى `ADMIN/is_admin` يعمل فقط عندما يكون `role_v2` فارغًا خلال فترة التوافق.
- أصلح جدول سياسات الأدوار: الموظف والمرفق لم يعودا يحصلان على كل مفاتيح الصلاحيات.
- أصبحت مفاتيح مثل `manage_users` مقفلة للموظف والمرفق حتى لو وُجدت بقيمة true داخل JSON قديم أو مُرسل.

## عزل اختبارات التكامل

- `npm run test:integration` يستخدم مشغلًا مستقلًا يفحص `TEST_DATABASE_URL` ثم يفرضه كـ`DATABASE_URL` داخل Vitest.
- يرفض اسم قاعدة لا يحتوي علامة مستقلة `test` أو `testing`.
- لا توجد إمكانية لاستخدام `.env` التطويرية ضمن عملية integration بعد نجاح الحاجز.

## مخاطر وحدود حالية

- وجود الطبقة المركزية لا يعني أن كل المسارات تستخدمها بعد؛ هذه مهمة المرحلة الثالثة.
- أي Route أو Server Action ما زال يفحص `is_admin` مباشرة قد يتجاوز `role_v2`، ويجب نقله تدريجيًا.
- المرافق والموظفون بلا `AccountServiceAccess` سيُرفض وصولهم عند تفعيل نطاق الخدمة على المسار؛ يجب تعبئة الخدمات المعتمدة قبل إغلاق تلك المسارات.

## خطة المرحلة الثالثة

الدفعة الأولى عالية الخطورة:

1. صادرات المستفيدين والحركات والخدمات الثلاث.
2. قراءة المستفيد وحركاته عبر API.
3. Server Actions للأسنان والبصريات والعلاج الطبيعي.
4. الاستيراد والتراجع للمسارات الثلاثة.
5. حماية `/api/debug-dental` وتعطيله افتراضيًا.

بعد كل دفعة تُشغّل اختبارات رفض cross-company على النسخة الاختبارية وتُقارن أعداد السجلات والمال دون تعديل بيانات الإنتاج.
