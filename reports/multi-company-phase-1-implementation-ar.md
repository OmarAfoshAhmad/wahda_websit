# تقرير تنفيذ المرحلة الأولى

تاريخ التنفيذ: 2026-07-16.

## ما تغير

- أضيف enum انتقالي `AccountRole` بالقيم: `SUPER_ADMIN`, `COMPANY_ADMIN`, `MANAGER`, `EMPLOYEE`, `FACILITY`.
- أضيف `Facility.role_v2` اختياريًا، مع إبقاء `role` والأعلام القديمة دون تغيير لضمان التوافق.
- أضيفت علاقتا `parent_manager_id` و`created_by_id` اختياريًا لتنظيم موظفي كل مدير وتتبع منشئ الحساب، كما في تنظيم مشروع الواحة.
- أضيف `AccountCompanyAccess` بعلاقة many-to-many، وقيد فريد `(account_id, company_id)`، ومعلومة المنشئ وصلاحيات JSON اختيارية.
- أضيف `AccountServiceAccess` لفصل نطاق الخدمة المسموح للحساب عن نطاق الشركات.
- أضيف `FacilityServiceCapability` لأن المرفق الواحد، وخصوصًا المستشفى، قد يقدم أكثر من خدمة.
- أضيف `company_id` اختياريًا إلى `AuditLog`, `ImportJob`, `RestoreJob` مع FK من نوع `SET NULL` وفهارس زمنية حسب الشركة.
- أضيفت migration توسعية فقط في `20260716120500_expand_account_company_scope`؛ لا تحتوي backfill أو حذفًا أو `NOT NULL` جديدًا.
- أضيف سكربت `npm run audit:company-scope` للتدقيق read-only. يتطلب `AUDIT_DATABASE_URL` صراحة ويتجاهل `DATABASE_URL` لمنع الاتصال العرضي.

## سلوك dry-run

- يصنّف تحويل الدور إلى `safe`, `ambiguous`, أو `unresolved`.
- لا يعتبر الأدوار النصية غير المعروفة صالحة للـ enum.
- لا يقترح `SUPER_ADMIN` إلا للحساب المطابق صراحة لـ `SUPER_ADMIN_ACCOUNT_ID`; وجود `is_admin` القديم وحده غير كافٍ.
- يقترح منح كل المديرين الحاليين المعروفين بأمان جميع الشركات مبدئيًا، مع إبقاء إمكانية تقليصها لاحقًا.
- يقترح خدمة المرفق من `facility_type` فقط للأنواع التخصصية الصريحة؛ المستشفى و`AUTO` يحتاجان مراجعة متعددة الخدمات.
- يحصي السجلات بلا شركة وعدم تطابق شركة الحركة/المطالبة مع المستفيد.
- لا يقترح وصول شركة للحساب تلقائيًا، ولا يملأ الشركة في Audit/Import/Restore، لأن الأدلة الحالية قد تكون ملتبسة.
- يبدأ transaction بـ `SET TRANSACTION READ ONLY` ولا توجد فيه أي عملية create/update/delete.

## تطبيق بيئة التطوير

- طُبقت migration بتاريخ 2026-07-16 على قاعدة التطوير المحلية `wahda_db` باستخدام `prisma migrate deploy`.
- اتصال التطوير محلي ومختلف عن اتصال `.env.production`. يوصى لاحقًا بإعادة تسمية القاعدة باسم يحمل `dev` بوضوح.
- طُبقت قبلها migration القديمة `20260603070549_sync_schema` لأنها كانت معلقة، وهي migration محايدة وفارغة.
- لم يُنفذ أي backfill أو تعديل على السجلات المالية.
- baseline قبل التطبيق: 16 شركة، 333 حسابًا، مستفيد واحد بلا شركة، 2104 حركات بلا شركة، ولا مطالبات بلا شركة.
- توجد 3 حسابات admin قديمة تحتاج تحديد حساب المبرمج بينها عبر `SUPER_ADMIN_ACCOUNT_ID`.
- توجد حالة دور واحدة ملتبسة بين `MANAGER` و`FACILITY`.
- تعبئة المديرين المقترحة بعد حسم الدور: 144 علاقة وصول (المديرون المعروفون × 16 شركة).

## قرار حساب المبرمج ونسخة الإنتاج الاختبارية

- أكد المستخدم أن حساب `admin` / `System Admin` هو المبرمج الوحيد `SUPER_ADMIN`.
- الحسابان الإداريان القديمان `admin_benghazi` و`admin_tripol` يعاملان كمديرين، وليس كمبرمجين.
- أضيف سكربت `backfill:company-scope` بوضعي preview و`--apply`، ولا يعمل إلا مع `TEST_DATABASE_URL` واضح و`SUPER_ADMIN_ACCOUNT_ID` صريح.
- لا يغير السكربت أعلام/أدوار التوافق القديمة، ولا يلمس المستفيدين أو الحركات أو المطالبات أو المحافظ.
- استعيدت نسخة إنتاج سليمة في قاعدة محلية مستقلة `waad_production_snapshot_test`، وتطابقت بصمة SHA-256 قبل الاستعادة.
- طُبقت migration الجديدة بنجاح على النسخة، ثم نُفذ backfill داخل transaction واحدة.
- النتيجة: `admin` هو `SUPER_ADMIN` الوحيد، و13 مديرًا نشطًا لديهم 195 علاقة وصول إلى 15 شركة غير محذوفة، بلا تكرار.
- بقيت الأعداد قبل وبعد مطابقة: 16 شركة، 368 حسابًا، 38,009 مستفيدين، 2,751 حركة، و0 مطالبات.
- سُجلت عملية backfill مرة واحدة في `AuditLog`.
- توجد حركتان شركتهما لا تطابق شركة المستفيد؛ لم تُعدلا وتحتاجان تقرير مراجعة مستقلًا.
- تاريخ الإنتاج يحتوي خمس محاولات rolled-back لـ`20260618062000_sync_tpa_production_fields`. الملف حُذف عمدًا في Git بعد فشلها؛ لم يُعد تشغيله، ولم يمنع `migrate deploy` من تطبيق migration الجديدة على النسخة الاختبارية.

## قرارات بيانات لازمة قبل التعبئة

1. يجب تحديد `SUPER_ADMIN_ACCOUNT_ID` لحساب المبرمج الوحيد؛ بقية حسابات admin القديمة لن تُرقّى تلقائيًا.
2. المديرون الحاليون يحصلون على جميع الشركات في التعبئة الأولية، ثم يمكن تقليص نطاق كل مدير لاحقًا. الموظفون والمرافق يحتاجون تعيينًا صريحًا أو قاعدة معتمدة.
3. سجلات `company_id = null` وحالات عدم التطابق المالية يجب تصنيفها ومراجعتها قبل أي backfill.
4. `RestoreJob` قد يمثل نسخة متعددة الشركات؛ إبقاء `company_id = null` يمكن أن يعني global، ويجب تعريف هذا المعنى رسميًا.

## قرار وضع مصرف الوحدة

- متغير البيئة الحالي يبقى آلية توافق مؤقتة ولا يصبح مصدر تفويض أو عزل.
- النموذج النهائي موحد: مصرف الوحدة شركة ضمن الشركات، ويمكن إضافة مخصصاته إلى `ServicePolicy` والمحافظ لاحقًا.
- إزالة تبديل الوضع مستقبلًا لا تتطلب تغيير نموذج الحسابات أو الخدمات؛ نطاق الشركة والخدمة مشتقان من قاعدة البيانات.
- الصلاحيات الوظيفية، نطاق الشركات، ونطاق الخدمات محاور مستقلة. رؤية مرافق الأسنان مثلًا تعتمد على `FacilityServiceCapability(DENTAL)`، لا على كون `facility_type = DENTAL` فقط.

## الخطوة التالية المقترحة

تشغيل migration أولًا على قاعدة اختبار مستقلة أو نسخة مستعادة فقط، ثم تشغيل dry-run عليها وحفظ الناتج للمراجعة. بعد اعتماد النتائج تبدأ المرحلة الثانية: طبقة التفويض المركزية واختبارات رفض الوصول بين شركتين. لا يجوز تشغيل migration أو backfill على الإنتاج في هذه الخطوة.
