# تحليل النسخ الاحتياطي والاستعادة للمنظومة الحالية

## سبب الخطأ الحالي

رسالة:

`data.transactions.0.type — Invalid option`

سببها أن تحقق ملف النسخة داخل التطبيق كان يقبل أنواع الحركات القديمة فقط:

- `MEDICINE`
- `SUPPLIES`
- `IMPORT`
- `CANCELLATION`
- `SETTLEMENT`

بينما قاعدة البيانات الحديثة تحتوي أيضًا:

- `DENTAL`
- `OPTICS`
- `GENERAL`
- `PHYSIOTHERAPY`

تم تحديث التحقق ليقبل الأنواع الحديثة، لكن هذا لا يجعل استعادة `.wbk` وحدها كافية لكل سيناريوهات تعدد الشركات.

## تقييم آليات النسخ الموجودة

### 1. نسخة قاعدة البيانات الكاملة `pg_dump / pg_restore`

هذه هي الآلية الأفضل حاليًا للنسخة الإنتاجية أو لاختبارات التطوير لأنها تحفظ كل شيء كما هو:

- الشركات
- المستفيدين
- الحركات
- الصلاحيات
- جداول الخدمات
- المخصصات والمحافظ
- سجلات التدقيق
- المفاتيح والعلاقات

هي الأسرع والأكثر دقة عند نقل نسخة الإنتاج إلى بيئة تطوير أو عند استعادة النظام بالكامل.

### 2. نسخة التطبيق `.wbk`

هذه مفيدة كنسخة محمولة من داخل الواجهة، لكنها في وضعها الحالي ليست كاملة كنسخة تعدد شركات حديثة. التصدير الحالي يركز على:

- المستخدمين / المرافق
- المستفيدين
- الحركات
- سجل التدقيق
- الإشعارات

ولا يغطي بشكل كامل كل الحقول والجداول الحديثة مثل:

- `company_id` في كل المسارات المهمة
- `role_v2`
- صلاحيات الشركات والخدمات
- سياسات الخدمات
- جداول المحافظ والاستهلاك
- أرشيف استيراد العائلات
- خرائط وأنواع الخدمات

لذلك لا أنصح باستخدام `.wbk` كاستعادة إنتاجية كاملة قبل تحديثها.

## أفضل السيناريوهات

### السيناريو الأفضل للتطوير

استخدم نسخة `pg_dump` من الإنتاج ثم استعدها في قاعدة تطوير منفصلة مثل:

`waad_replace_cycle_test`

هذا هو المسار الذي نستخدمه الآن، وهو الأنسب لإدارة مشاكل كل شركة على حدة دون لمس الإنتاج.

### السيناريو الأفضل للطوارئ الإنتاجية الكاملة

استخدم `pg_restore` أو `psql` لاستعادة قاعدة كاملة إلى قاعدة جديدة، ثم بدّل التطبيق إليها بعد التحقق.

لا تستعد فوق قاعدة الإنتاج مباشرة إلا عند الضرورة القصوى وبعد نسخة احتياطية جديدة.

### استعادة شركة واحدة

ممكنة، لكنها ليست مجرد زر “استعادة شركة”؛ لأن الشركة مرتبطة بجداول كثيرة:

- `InsuranceCompany`
- `Beneficiary`
- `Transaction`
- `WalletConsumption`
- `Claim`
- `ServicePolicy`
- `ServiceTypeMapping`
- `FamilyImportArchive`
- `AuditLog`
- صلاحيات الحسابات المرتبطة بالشركة

الأفضل أن تنفذ كأداة مخصصة:

1. نحدد الشركة بالـ `company_id`.
2. نقرأ بياناتها من قاعدة snapshot منفصلة.
3. نعمل dry-run يوضح عدد السجلات التي ستضاف أو تحدث أو تتخطى.
4. ننفذ upsert داخل transaction.
5. لا نحذف بيانات خارج الشركة.
6. نولد تقرير قبل/بعد.

## التوصية العملية

حاليًا:

1. اعتمد `pg_dump/pg_restore` للنسخ الرسمية والاختبارية.
2. لا تعتمد `.wbk` للاستعادة الإنتاجية الكاملة قبل تطويرها.
3. نضيف لاحقًا أداة `restore-company-from-snapshot` لاستعادة شركة واحدة من قاعدة snapshot، وهذا أنظف من محاولة قص ملف `.wbk`.
4. نحدث `.wbk` ليصبح نسخة تطبيق حديثة تشمل كل جداول تعدد الشركات والخدمات.

## قرار هندسي مقترح

لعملك الحالي في إصلاح المنظومة وإدارة مشاكل الشركات:

- أبقِ بيئة التطوير مطابقة للإنتاج عبر `pg_restore`.
- نفذ الإصلاحات والتحقق على `waad_replace_cycle_test`.
- عند الحاجة لاستعادة شركة واحدة، نستخدم snapshot منفصل كمصدر ونبني أداة موجهة للشركة.

هذا يقلل خطر المديونية أو خلط الشركات، ويجعل كل اختبار قابلًا للإعادة.

## أداة مبدئية لاستعادة شركة واحدة

تمت إضافة سكربت:

`scripts/restore-company-from-snapshot.js`

الاستخدام الافتراضي آمن ويعمل كتقرير فقط:

```powershell
$env:SOURCE_DATABASE_URL="postgresql://postgres:password@localhost:5432/waad_production_snapshot_test"
$env:TARGET_DATABASE_URL="postgresql://postgres:password@localhost:5432/waad_replace_cycle_test"
node scripts/restore-company-from-snapshot.js --company-code=JFZ
```

للتنفيذ الفعلي على قاعدة تطوير فقط:

```powershell
node scripts/restore-company-from-snapshot.js --company-code=JFZ --apply
```

السكربت لا يحذف بيانات خارج الشركة، ويعتمد `upsert` للسجلات المرتبطة بالشركة.
